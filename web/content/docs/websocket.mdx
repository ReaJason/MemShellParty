## WebSocket（JSR-356）

Java WebSocket 1.0（JSR 356）把 Endpoint 的注册交给中间件：容器启动时初始化
`ServerContainer` 并放进 `ServletContext`（javax 命名空间的 key 为
`javax.websocket.server.ServerContainer`，jakarta 为 `jakarta.websocket.server.ServerContainer`）。
注入器反射取到该容器后，用 `ServerEndpointConfig.Builder` 构建配置并调用 `addEndpoint`
注册恶意 `Endpoint`：

```java
Object container = invokeMethod(servletContext, "getAttribute",
        new Class[]{String.class}, new Object[]{"javax.websocket.server.ServerContainer"});
Object builder = invokeMethod(ServerEndpointConfig.Builder.class, "create",
        new Class[]{Class.class, String.class}, new Object[]{shell.getClass(), urlPattern});
invokeMethod(container, "addEndpoint",
        new Class[]{ServerEndpointConfig.class},
        new Object[]{invokeMethod(builder, "build", null, null)});
```

Endpoint 只需要实现 `onOpen` / `onMessage`：WebSocket 帧由容器负责，消息回调里执行命令或转发字节流。
这条路线依赖容器自带的 WebSocket 实现，Tomcat 7+、Undertow、WebLogic 12+、GlassFish 4+ / Payara 5+、BES、
TongWeb、WebSphere 9+ / Liberty、Jetty 9.1+、InforSuite 9/10、Apusic 9.0 均可使用。Jetty 12 默认不加载
WebSocket 模块，需要启动时启用对应的 `eeN-websocket-javax` / `eeN-websocket-jakarta` 模块。

Nginx 或 CDN 默认不会转发逐跳头部 `Upgrade` 和 `Connection`，直连可用的 WebSocket 马放到反向代理
后面会握手失败；这种场景请使用 RawWebSocket。


## RawWebSocket（Tomcat 5 ~ 11 / BES / TongWeb / Undertow / GlassFish / Payara / Jetty）

RawWebSocket 不经过容器的 WebSocket 实现，而是由 helper 反射拿到当前 Connector 的底层连接后自己写 101
响应、跑帧循环。shell 只认 `GET` + `Sec-WebSocket-Key`，不依赖可能被 Nginx/CDN 剥离的 `Upgrade`
与 `Connection`，因此同一份马既能直连也能放在反向代理后面使用。
helper 会按 coyote buffer 的实际类型自动选择后端，不需要事先知道 Tomcat 版本或 Connector：

- Tomcat 5/6/7/8.0 的 BIO：`InternalInputBuffer.inputStream` / `InternalOutputBuffer.outputStream`；
- Tomcat 7/8.0 的 APR：`InternalApr*Buffer.socket` + `org.apache.tomcat.jni.Socket`；
- Tomcat 7/8.0 的 NIO：`NioChannel` + `NioSelectorPool`；
- Tomcat 8.0 的 NIO2：`SocketWrapper<Nio2Channel>` 的 Future 式 read/write；
- Tomcat 8.5+：`SocketWrapperBase` 的阻塞 read/write，覆盖 NIO / NIO2 / APR。

BES 9.5.2+ / 10 与 TongWeb 6/7/8 是改了包名的 Tomcat 分支。helper 不写死 `org.apache.*`
类名：ActionCode 从 `Response.action` 的形参反查，NioSelectorPool 的 read/write 按方法签名匹配，
BIO/APR/SocketWrapper 按 buffer 字段结构识别，因此这些分支的 BIO / NIO / SocketWrapper 后端可以直接复用。

生成期按 `<shellClassName>$RawWsHelper` 重命名 helper 并嵌入注入器；注入器先 defineClass helper 再实例化
shell。shell 以 GET + `Sec-WebSocket-Key` 触发，调用 `helper.equals(new Object[]{request, response, this})`
后由 helper 接管连接，helper 再反射回调 shell 的 `onReadBinary` / `onReadText` / `onDisconnect`。
容器相关的反射都收在 helper 里，Command/Godzilla/Proxy 的 shell 模板可以共用。

Tomcat 10/11 使用 `JakartaRawWebSocket`：模板仍是同一份 javax 源码，生成期由 JakartaPostProcessor 统一
重命名到 `jakarta.*` 命名空间，helper 本身只依赖 JDK。

JBoss AS 4~7.1 / EAP6 的 JBossWeb 是 Tomcat 分支，服务类型选择 JBoss 即可复用同一份 helper。
JBoss EAP7+ / WildFly 使用 Undertow：helper 从 servlet request/response 取出
`HttpServerExchange`，调用 `upgradeChannel` 让 Undertow 在刷出 101 响应后交出
`org.xnio.StreamConnection`，再由 helper 跑帧循环；同时强制 exchange 为持久连接，
避免 Nginx 把 `Connection` 改成 `close` 后连接被直接回收。helper 只依赖 JDK，
Undertow 1.x ~ 2.3.x 的 javax / Jakarta 部署共用同一份实现。

GlassFish/Payara 使用 Grizzly，helper 按连接器版本接管底层 `SocketChannel`：

- GlassFish 3 的 Grizzly 1.x：从 `com.sun.grizzly.tcp.Response.getChannel()` 取 channel，
  `suspend()` 后取消原 SelectionKey；
- GlassFish 4+ / Payara 的 Grizzly 2.x：从 `Request.getContext().getConnection()` 取
  `NIOConnection`，`detachSelectorRunner()` 后 `Response.suspend()`。

两代 Grizzly 都在写完 101 后用自己的 Selector 跑非阻塞帧循环，容器不再回收该请求。
GlassFish 3 ~ 8、Payara 5 ~ 7 已覆盖；Apusic/Primeton 等基于 GlassFish 二开的产品如果替换了连接器，
需要实测。

Jetty 6 ~ 12 的 RawWebSocket 从 `Request` 逐层找到 `EndPoint`，写完 101 后直接在 EndPoint 上跑
帧循环：Jetty 6/7/8 走 `org.mortbay.io.Buffer` / `org.eclipse.jetty.io.Buffer`，Jetty 9+ 走
`ByteBuffer`，TLS 由 Jetty 自身处理，javax / Jakarta 共用同一份 helper。

JakartaRawWebSocket。WebSphere 8.5.5 默认安装没有 `com.ibm.ws.wsoc`，需要额外安装
WebSocket 1.0 功能。Jetty 12 需要启动时启用对应的 `eeN-websocket-javax` / `eeN-websocket-jakarta`
模块。Apusic 9.0.1 没有 Tyrus，只能选择 RawWebSocket。RawWebSocket 与容器的 WebSocket 实现互不影响，
可以在同一容器里共存。

## 限制

- 仅支持 HTTP/1.1，不支持 HTTP/2 或 HTTP/3。
- 未实现 `permessage-deflate` 扩展与子协议协商。
- 单条消息上限 50 MB，超过时以 1009 关闭连接。
